## Problem

Every local business still runs on phone calls: bookings, questions, changes,
complaints, orders, availability. Owners miss calls; staff get interrupted; and AI
agents are risky because one bad answer (an over-promised allergy guarantee, a
hallucinated availability, a mis-routed 14-person party) loses revenue or creates
liability. So businesses don't trust AI on the phone.

## What we're building

A business owner pastes their website and connects a number. Otto extracts the
business rules into an `AgentSpec`, builds a voice agent, **attacks it with a swarm
of synthetic callers, finds the failure modes, patches its own policies, re-runs the
swarm, and only activates the phone line once it clears a safety gate.**

One-liner: **website in, self-healing inbound phone line out.**

## Refined vision (captured 2026-05-25, founder's words)

> Website + Relevant additional info → Swarm synthetic testing before any real calls
> (angled from the website's company type: a construction company gets one archetype of
> simulated callers, a restaurant a different sub-type — don't waste simulations on
> incorrect synthetic tests) → an inbound line that can scale infinitely, where each
> agent takes the company's specification (book a reservation / appointment, process a
> payment, deal with a refund) → and **every interaction gets evaluated** to see if
> anything went wrong; if it did, we run a swarm-heal on that specific thing with a huge
> volume of synthetic calls.

Four things this adds beyond the original plan:

1. **Input = website + additional info.** The website alone is thin. Best extra signals,
   in rough priority: **Google Business Profile** (hours, address, attributes, and reviews
   → real complaint patterns to seed the swarm); **the booking/POS platform** (OpenTable/
   Resy/Tock, Square/Toast, Calendly/Acuity → real actions + availability); **menu/service
   PDFs**; **a 60-second owner intake** (3 questions: which calls do you miss most? what
   must the agent never promise? when must it transfer to a human? → seeds policies +
   escalation directly); **Yelp/social** (failure modes customers actually hit); **the
   current voicemail/IVR** (tone + existing flows). All flow into the same `AgentSpec`.

2. **Vertical-archetyped swarm.** Persona selection is keyed on `business.type`. A
   contractor gets emergency-dispatch / quote / licensing-and-insurance / after-hours
   callers; a clinic gets appointment / insurance / "don't give medical advice" red-team;
   a restaurant gets allergy / large-party / availability. Cekura's scenario
   auto-generation (thousands of scenarios from the agent description) is the engine; the
   archetype guides it so every simulation is relevant. See `app/archetypes.py`.

3. **Each agent takes company-specified actions.** Tools generalize past reservations:
   `book_appointment`, `process_payment`, `handle_refund`, `dispatch_job`, plus
   reservations / SMS / escalate. The action set is part of the spec per business.

4. **Infinite scale + a perpetual production loop.** The inbound line runs on a host that
   scales 0 → thousands of isolated per-call sessions (AWS Bedrock AgentCore / Pipecat
   Cloud). **Every live call is evaluated** — not just the transcript but the whole
   **event stream** (a `CallTrace`): a rigorous failure taxonomy (`app/failure.py`,
   `docs/FAILURE_TAXONOMY.md`) classifies failures across four dimensions — conversation,
   action, outcome, experience — so a call where the voice was perfect but the *action* was
   wrong/slow/failed/unauthorized is caught. Each detected failure **authors its own policy
   fix**, which triggers a **targeted swarm-heal on that one thing** → patch → re-verify →
   redeploy. The line never stops getting safer. See `app/observe.py`.

So there are **two loops**: a broad pre-launch swarm gated before go-live, and a targeted
production swarm-heal that fires on real-world failures forever after. Full per-technology
detail in `docs/TECH.md`.

## The reframe (this is the whole game)

The original pitch framed self-healing as the "deeper magic" *behind* a "website to
phone in 30s" hook. For THIS hackathon that's backwards.

The hosts' brief, verbatim: *"The era of 'AI demos' is over. The next frontier is
production-grade AI agents. Cekura and Daily, in partnership with NVIDIA and AWS, are
challenging builders to bridge the gap between a voice agent that 'works' and an agent
that **scales, persists, and learns**."* They named four stages — **Build & Customize →
Deploy at Scale → Simulate & Evaluate → Auto-Improve** — and stated the judging
philosophy outright: *"We aren't just looking for the best-sounding voice; we are looking
for the best system."*

That brief is Otto's architecture written by the hosts. The eval→self-heal loop is the
exact thesis being judged, **Auto-Improve** is the headline stage, and Cekura — whose
product *is* "synthetic callers find failure modes" — is **co-hosting and in the room.**

So:
- **Lead with the hook** ("paste a website, get a phone line") because it's instantly
  legible to non-technical judges.
- **Win on the loop** (synthetic swarm → real failures → self-patch → re-run → gated
  activation → perpetual production heal), because that's stage 4 — the scored thesis and
  the co-host's home turf.
- **Build the loop on Cekura.** Pushing the co-host's own product to its limit in a
  closed loop is the strongest possible signal to the people scoring "the best system."
- **Speak the four stages back to them.** Map every layer of the demo to a named stage so
  a judge checks all four boxes without having to connect the dots themselves.

### Hard rule: the loop must be REAL

The one audience on earth that can smell a hardcoded `43% → 91%` is the Cekura team.
Every number on screen must come from an actual run. The patch must be a genuine
LLM-authored diff against genuine failure transcripts, followed by a genuine re-run.
We support this with no Cekura key (local LLM-caller + LLM-judge) and with real
Cekura — same data shapes, same honesty.

## Demo spine (cut everything not on this line)

1. Paste Piccino URL → extraction timeline streams real facts.
2. `AgentSpec` built; greeting + voice persona shown.
3. Swarm runs; caller cards animate pass/fail live (the money screen).
4. Failure map clusters 3 **hero failures**:
   - **Safety:** allergy guarantee too strong (red-team category).
   - **Booking:** 14-person party pushed through normal reservation flow.
   - **Knowledge:** agent guessed availability instead of calling the tool.
5. Auto-patch diff: before/after on the exact offending policies. Re-run. Pass rate climbs.
6. Activate Twilio number. **Judge calls it and asks the allergy question** — the
   one the swarm caught and the system patched — and it's handled correctly.

Everything else (8 verticals, gift cards, 6 separate screens) is a *spoken* "this
generalizes." Not built. One vertical, three hero failures, one mission-control screen.

## The AgentSpec (the spine)

`packages/spec/` — Pydantic source of truth, exported to JSON Schema + TS types.

- `business` — name, type, location, timezone, public_url, **disclaimer** (sandbox clone, public info, our own number, mock inventory).
- `voice` — persona, greeting, tts_voice.
- `knowledge[]` — {topic, content, source_url, confidence}.
- `capabilities[]` — reservations, order_pickup, gift_cards, faq, …
- `tools[]` — {name, description, params, mock_behavior} (check_availability, reserve_table, send_sms, escalate).
- **`policies[]`** — the patchable rules: {id, category(safety|booking|knowledge|voice_behavior), trigger, rule, severity}. **The self-heal loop edits only these.**
- `escalation_rules[]`, `safety_rules[]`, `out_of_scope[]`.
- `meta` — version, parent_version (lineage), timestamps.

The live system prompt is **compiled** from the spec (`spec.compile_prompt()`), so a
policy edit produces a clean before/after diff and a recompiled agent. That's what
makes the patch screen legible and the loop trustworthy.

## The self-heal loop

```
extract(url) ──▶ AgentSpec v1
                     │
        ┌────────────▼─────────────┐
        │ swarm.run(spec)          │   local: LLM caller ↔ compiled prompt ↔ LLM judge
        │  → per-persona pass/fail │   cekura: Cekura test framework over Daily WebRTC
        │    + reason + transcript │
        └────────────┬─────────────┘
                     │ failures
        ┌────────────▼─────────────┐
        │ heal(spec, failures)     │   LLM rewrites/adds policies → AgentSpec v2
        │  → policy diff (b/a)     │   (structured, reviewable, never freeform prompt soup)
        └────────────┬─────────────┘
                     │ re-run until pass_rate >= PASS_GATE or max rounds
                     ▼
              activate(Twilio)        only past the gate
```

Persona suite (`apps/orchestrator/app/swarm.py`): severe-allergy, last-minute table,
14-person party, "are you open now?", vegan options, price-shopper, interrupter,
Spanish speaker, bad-audio/garbled, private-event, refund/complaint, dog question.
Each carries success criteria an LLM-judge (or Cekura metric) scores.

exists at this event — open models earn credit through the NVIDIA-accelerated path.)

## Risks & mitigations

| Risk | Mitigation |
|---|---|
| "30s" includes the swarm (it can't) | Reframe: 30s to a working agent, *then* watch it harden. Don't claim end-to-end 30s. |
| Faked loop sniffed by Cekura judges | Loop is real in both modes; nothing hardcoded. |
| Live extraction flaky (Piccino is JS/Squarespace) | Real crawler+extractor AND cached `piccino.json` fallback. |
| Live-call latency | Fast STT/TTS + small fast LLM; pre-warm pipeline; corner NVIDIA mentor on NIM. |
| Pipecat setup eats the clock | Start from `pipecat-quickstart-phone-bot`; orchestrator + dashboard + loop are stack-independent and built first. |
| Python 3.14 lacks ML wheels | Pin agent venv to 3.12 via uv. |
| Legal (real restaurant) | Disclaimer baked into spec + greeting; our number; mock inventory. |
